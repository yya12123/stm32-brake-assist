# 阶段① 接线（修订版 · 对照你当前画面）

> 上一版有三处问题，先纠正：
> 1. **没提醒 "Hide All" 属性坑** —— 双击 BLUEPILL 后如果看不到 Program File，是属性被折叠了；
> 2. **没让你先清掉芯片版的残留** —— C1/C2/C3/X1/R1/R2 这些是原来 U1 芯片方案留下的，现在悬空，就是那 2 个错误的来源；
> 3. **旋转按钮的位置描述不准** —— 改成更稳的说法。

## 一、先说结论：你的接线是对的

对照截图，这条链路已经通了：

    VDD ──── D1(绿灯) ──── R3(330Ω) ──── PC13(2脚)

**接线部分不用重做。** 剩下的是"固件没加载"和"悬空元件报错"这两件事。

## 二、当前画面上的元件清点

| 元件 | 位置 | 状态 | 怎么处理 |
|---|---|---|---|
| **U2 BLUEPILL** | 中间 | 留着 | 主角 |
| **D1 LED-GREEN** | 右中 | 留着 | 已连好 |
| **R3 330** | 右侧 | 留着 | 已连好 |
| **VDD（右边那个）** | 右上 | 留着 | 已接到 D1 |
| **VDD（左边那个）** | 中间偏左 | 悬空 | **删掉** |
| **GND** | 中间 | 悬空 | **删掉** |
| **C1 / C2 / C3** | 左上 | 芯片方案残留 | **删掉** |
| **X1 CRYSTAL** | 左侧 | 芯片方案残留 | **删掉** |
| **R1 10k / R2 10k** | 上、左下 | 芯片方案残留 | **删掉** |

> 为什么删：这些是原来"U1 STM32F103C8 + 晶振 + 复位"方案用的。现在改用 BLUEPILL（板载已经集成晶振和复位），它们就是一堆悬空引脚——Proteus 会报 ERC 错误，而且仿真时毫无用处。
>
> **删法**：左键点中 → 按键盘 Delete 键。一次删一个，删完再点下一个。

## 三、加载固件（关键步骤，也是唯一没做的）

### 3.1 双击 U2

弹出 **Edit Component** 窗口。

### 3.2 如果看不到 Program File，先把属性展开

窗口下半部分有一个属性列表，左上角通常有个 **"Hide All"** 复选框。

- 如果它是**勾选**状态 → **取消勾选**，属性就全部显示出来了
- 展开后你会看到类似这些项：
  - Program File（程序文件）
  - Clock Frequency（时钟频率）

### 3.3 填两项

| 属性 | 填什么 |
|---|---|
| **Program File** | 点该行右边出现的小文件夹图标 → 选 C:\temp\fw.hex |
| **Clock Frequency** | 8M（有的版本显示 8MHz） |

> hex 我已经放在 C:\temp\fw.hex（纯英文路径）。
> 备用：C:\temp\fw_8mhz.hex

点 **OK**。

## 五、运行

点左下角 **▶**（或按 **F12**）。

### 预期现象

> 注意：固件里是**低电平点亮**，也就是 PC13 拉低时灯亮。所以你看到的节奏是——大部分时间灭，隔 0.5 秒闪一下。这是正常的。

## 六、2 Error(s) 是怎么回事

左下角那个红色 ✖ 是**电气规则检查（ERC）**报错，不是仿真错误。

**怎么看到底错在哪：**

1. 点左下角那个红色 ✖ 或者它旁边的 "2 Error(s)" 文字
2. 会弹出 ERC 报告窗口，逐条列出（一般是 Pin ... is not connected 之类）

**大概率就是这些：**

- C1/C2/C3/X1/R1/R2 的引脚悬空
- 左边那个没接线的 VDD 和 GND

**把第二节列的元件删干净，错误数就会归零。**

## 附：为什么不走芯片方案了

之前那份《Proteus仿真搭建手册》是按 **U1 = STM32F103C8 裸芯片** 写的，需要外接 8M 晶振、22pF×2、复位电阻电容、BOOT0 下拉、VDD/VSS 共 8 个引脚接电源 —— 二十多根线，手工连很容易错。

改用 **BLUEPILL 最小系统板模型** 后：晶振、复位、供电全部在板子内部，只剩下 3 根线要接。而且 **你最终要买的实物板就是这一块 Blue Pill**，仿真和实物完全对应，论文里也好写。

所以：**U2 是最终方案，U1 那套作废。**

## 九、运行后"亮一下、灭二三十秒"是怎么回事

**这是正常的，而且证明固件在跑。**

先看数据：你看到的是"亮 0.5 秒、灭 20~30 秒"，占空比约 **2%**。
固件里运行灯原本就是 **亮 10ms / 灭 490ms**，占空比 **2%**。比例完全吻合，只是整体被拉长了几十倍。

原因是两件事叠加：

1. **Proteus 的 STM32 模型跑不到实时** —— 它是一条指令一条指令解释执行的，实测算下来通常只有真实速度的 1/5 ~ 1/50；
2. **可能还有时钟不匹配** —— 如果你的 Clock Frequency 填的是 8MHz，而固件是按 72MHz 配置的（PLL ×9），那么软件里"500ms"在仿真里会被拉长 9 倍。

### 怎么确认

看 Proteus 窗口**底部状态栏右侧**的仿真时间显示（Time: ...）。
让它跑 10 秒真实时间，看仿真时间走了多少毫秒：

- 走了 1000ms 左右 → 基本实时，速度没问题
- 走了 100~200ms → 跑了 1/5 ~ 1/10 速度，属于正常
- 走了 20~50ms → 跑了 1/50，太慢，用下面的办法

### 解决办法：换 fw_demo.hex

我做了一个**演示友好版**，两处改动：

| 项 | 改动 | 效果 |
|---|---|---|
| 时钟 | 改成 8MHz 运行（不再用 PLL） | 仿真速度快约 9 倍 |
| 心跳 | 改成亮 0.5 秒 / 灭 0.5 秒（50% 占空比） | 肉眼一眼就能看出在闪 |

**用法**：双击 U2 → Program File 改成 `C:\temp\fw_demo.hex` → Clock Frequency 保持 **8M** → OK → 重新运行。

预期：**规律地一闪一闪，大概每 1~5 秒一个完整周期**（取决于 Proteus 跑多快），但一定是均匀的、肉眼可见的节奏。

### 说明

- `fw.hex` = 72MHz 完整版，**将来烧到实物板上用这个**
- `fw_demo.hex` = 8MHz 演示版，**只在 Proteus 里看效果用**

论文里可以写一句："为降低仿真计算量，仿真阶段采用 8MHz 主频，实物采用 72MHz"——这反而显得你想过这个问题。
